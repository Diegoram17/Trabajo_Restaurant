# Exploration: BACKLOG #3 — Arranque, administrador y dispositivo (arranque-admin-dispositivo)

## Current State

**What exists today (merged: #1 `3ea1d54`, #2 `76729cc`).**

Backend is a minimal, framework-less `node:http` server (`src/server/index.ts`) with a fixed 5-step
pipeline: forwarded-cleartext rejection → Origin guard (`src/server/http/origin-guard.ts`, ADR-0033 §3,
already generic — covers any future mutation for free) → `/trpc/*` via `@trpc/server/adapters/node-http`
→ static SPA assets (`src/server/http/static.ts`, path-containment enforced) → SPA entry document only for
`Accept: text/html` → 404. Binds to `127.0.0.1` only (`DEFAULT_BIND_HOST`, ADR-0041).

Data access is Kysely (ADR-0042) wrapping the existing `pg.Pool` (`src/server/db/kysely.ts`,
`src/server/db/pool.ts`). Types are generated by `kysely-codegen` into the committed
`src/server/db/schema.d.ts` and drift-checked by `tests/integration/schema-types.test.ts` on every
`npm test` run (no CI in this project — that test IS the gate). tRPC `Context`
(`src/server/trpc/context.ts`) currently carries only `{ db: Kysely<DB> }` — no request/response object,
no auth/session state of any kind. `src/server/trpc/app-router.ts` has one throwaway `ping`/mutation
procedure only; no real domain router exists yet.

Migrations are plain numbered `.sql` files in `migrations/`, applied forward-only, transactional per
file, tracked in `schema_migrations` (`scripts/migrate.ts`). Two exist:

- `0001_configuracion.sql` — creates `configuracion_costos`, `calendario_apertura`,
  `calendario_apertura_excepcion`, `configuracion_operativa`, all empty, no seed rows, no column has a
  `DEFAULT`. `creada_por` ships as `integer NOT NULL` **without its FK**, with an explicit comment:
  *"Persona does not exist until item #3, which adds the constraint, recorded on BACKLOG row #3."* This
  is the exact debt item #3 is scoped to repay.
- `0002_dia_operativo_y_vigencia.sql` — adds `dia_operativo()` (SQL, STABLE) and a
  `BEFORE INSERT OR UPDATE OF vigente_desde` trigger (not a `CHECK`, deliberately, for `pg_dump`/
  `pg_restore` and table-rewrite safety) enforcing forward-only `vigente_desde` on both versioned config
  tables.

**Nothing auth-related exists yet**: no `Persona`, no `Dispositivo`, no session/cookie code, no
password-hashing dependency. `package.json` has zero of `argon2`, `@node-rs/argon2`, `bcrypt`, or
`cookie` — only `pg`, `kysely`, `@trpc/*`, `zod`, `react*`. This is a real gap the design phase must
close, not an oversight to work around.

**Testing convention (ADR-0038)**: Vitest; anything touching concurrency/FIFO/money runs against real
PostgreSQL via `tests/setup/global-setup.ts`, which invokes the real `runMigrations()`. Existing test
names show an established "positive contract + negative-space" pairing style
(`sin-sql-interpolado.test.ts`, `sin-redondeo-suelto.test.ts`) worth mirroring for the new auth surface
(e.g. a `sin-payload-sql-interpolado` equivalent for the password/token write paths).

**Governing ADRs already fully resolve the hard design questions** — item #3 is implementation of
decisions already made, not new architecture:

- **ADR-0034** — anchors PIN attempts by dispositivo (device cookie required, checked before comparing
  PIN), anchors `/admin` attempts by cuenta+IP (no device required), and closes the bootstrap
  circularity explicitly (no seeded device, no first-run mode; `/admin` never enrolls itself because
  `Dispositivo.rol` has no `admin` value).
- **ADR-0033/0037** — exact cookie attributes: device cookie `Secure·HttpOnly·SameSite=Lax`; `/admin`
  session cookie `Secure·HttpOnly·SameSite=Strict`; `Origin` validated on every mutation (already
  implemented, generic, reusable as-is).
- **ADR-0041** — dev has no TLS; process binds loopback plaintext; the obligation to verify
  `Secure`/`SameSite` attribute correctness on the emitted `Set-Cookie` header is explicitly this item's
  job (and #5's), not #1's — #1 shipped with zero cookies.
- **ADR-0036** — hashing split is exact: Argon2id + per-credential salt for the three low-entropy
  secrets (PIN mesero, PIN cocina, admin password — cocina PIN is item #11's, mesero PIN is #5's; only
  the admin password is this item's); SHA-256 + salt (explicitly NOT a KDF) for the ≥128-bit CSPRNG
  device token, because the token is checked on every stream request.
- **ADR-0042** — Kysely's `sql` template binds every value, so money/vigencia writes are parameterized
  by construction; no new decision needed there.

## Affected Areas

- `migrations/000X_persona_y_dispositivo.sql` (new) — creates `Persona` (at minimum: admin-relevant
  columns), `Dispositivo`, and whatever lockout/session-state table(s) the design settles on. Must add
  the FK `configuracion_costos.creada_por → persona.id` and `calendario_apertura.creada_por → persona.id`,
  closing #1's deferred debt (comment in `0001_configuracion.sql` is the literal marker).
- `migrations/000X_seed_configuracion_y_admin.sql` **can't be a pure `.sql` migration** — see Risks: the
  admin seed needs an Argon2id hash and a one-time-shown plaintext password, which `scripts/migrate.ts`'s
  "execute static `.sql` file" model has no mechanism to produce or print. A parallel TypeScript seed
  step is a new piece of infrastructure, not a new migration file.
- `src/server/db/schema.d.ts` — regenerated via `npm run db:types` after every new migration (manual
  step per ADR-0042's design; the drift test enforces it, does not automate it).
- `src/server/trpc/context.ts` — currently `{ db }` only; will need request/response access (to read/
  write cookies) and/or a session-verification hook, which changes its shape for every downstream item.
- `src/server/trpc/router.ts` / `app-router.ts` — needs new procedure variants (something like an
  `adminProcedure` requiring valid session, distinct from `publicProcedure`) and the real login/rotate-
  password/enroll-device/rotate-device/revoke-device endpoints.
- `src/server/index.ts` — the pipeline may need a new step or context-building change to parse `Cookie`
  and set `Set-Cookie`; currently nothing in the pipeline touches cookies.
- `package.json` — needs a password-hashing dependency (none installed) and likely a
  cookie-serialization dependency; see Approaches.
- New modules analogous to `origin-guard.ts`/`static.ts` in style: something for password
  hashing/verification, session cookie issue/verify, device-token issue/verify, and lockout-counter
  bookkeeping.
- `tests/integration/` and `tests/unit/` — new test files following the established
  real-Postgres-for-anything-stateful convention (ADR-0038); `tests/setup/global-setup.ts` may need to
  also run the new seed step so the suite has a known admin fixture.
- `adrs/` — item #3 is pure implementation of ADR-0031/0033/0034/0036/0037/0041/0042; it should not need
  a new ADR unless the propose phase makes a genuinely new architectural choice (e.g., the exact
  session-storage mechanism, which the ADRs do not specify — see Risks).

## Approaches

1. **Hand-rolled, minimal, no new HTTP framework** — extend the existing `node:http` pipeline with small
   purpose-built modules (session-cookie parse/sign, password-hash wrapper, lockout-counter store), same
   pattern as `origin-guard.ts`/`static.ts`. Zero new runtime dependency beyond a hashing library.
   - Pros: consistent with the project's established "one clear module per concern, no framework"
     architecture (ADR-0001, ADR-0037); nothing to reconcile with the existing pipeline's ordering
     guarantees; fully testable with the existing Vitest+real-Postgres convention.
   - Cons: cookie serialization/parsing and session-token integrity checks are exactly the kind of
     security-sensitive plumbing that's easy to get subtly wrong by hand (e.g., cookie attribute
     quoting, signature comparison timing).
   - Effort: Medium-High (several new modules, 2-3 new tables, ~5 new endpoints: seed-visible-once,
     login, rotate-password, enroll/rotate/revoke device).

2. **Hand-rolled auth logic + two small, focused dependencies** — add `@node-rs/argon2` (napi-rs
   prebuilt binaries, no native build toolchain needed — relevant on a Windows dev machine, unlike the
   plain `argon2` package which needs `node-gyp`) for Argon2id, and the tiny `cookie` package for
   `Set-Cookie`/`Cookie` header serialization/parsing (the actual session/lockout/device-verification
   logic stays hand-written, same as approach 1).
   - Pros: removes the highest-risk hand-rolled pieces (cookie attribute correctness, Argon2 binding)
     without adding a framework; `@node-rs/argon2` avoids the Windows build-toolchain friction the plain
     `argon2` package has.
   - Cons: two new runtime dependencies to justify and pin; still need to design the session-state
     storage mechanism from scratch (no ADR specifies it — see Risks).
   - Effort: Medium.

3. **Migrate to a framework with built-in session middleware** (Express/Fastify + `express-session` or
   equivalent).
   - Pros: mature, well-audited session handling out of the box.
   - Cons: contradicts ADR-0001/ADR-0037's committed single-process minimal architecture; the existing
     origin-guard/static-serving pipeline, its tests (`tests/integration/http-pipeline.test.ts`,
     `routes.test.ts`, `transport.test.ts`), and #1/#2's whole surface would need rework this late for no
     architectural gain — ADR-0033/0034 already specify the exact cookie semantics needed, which a
     framework would abstract rather than simplify.
   - Effort: High, disproportionate to this backlog item's scope.

## Recommendation

**Approach 2.** Keep the existing minimal `node:http` + tRPC pipeline untouched in shape; add
`@node-rs/argon2` and `cookie` as the only two new dependencies; hand-write session/device-
verification/lockout-counter logic as small dedicated modules mirroring `origin-guard.ts`'s style (one
exported pure-ish function per concern, unconditionally wired into the pipeline rather than an opt-in
per-procedure middleware, following the same "the dominant failure mode is not propagating a decision"
lesson this project has already internalized twice). This is the smallest change consistent with
ADR-0001/0033/0034/0036/0037/0041/0042 and reopens none of them.

## Risks

Open design questions the propose/spec/design phases must resolve — not resolved here by design:

1. **Argon2id library choice is unmade.** No hashing dependency exists in `package.json` today.
   Candidates: `@node-rs/argon2` (prebuilt native, no build toolchain — favors the Windows dev
   environment), `argon2` (node-gyp native build, more common but build friction), `@phc/argon2` (pure
   JS, slow). This is a real, unresolved decision, not a formality.
2. **Session-storage mechanism is unspecified by every ADR.** ADR-0031/0033 fix the cookie attributes
   (`Secure·HttpOnly·SameSite=Strict`, 60 min inactivity) but never say where the session state lives: a
   signed/stateless cookie (session id + expiry + HMAC, sliding-window renewal per request) vs. a
   server-side session table (revocable instantly, but a new entity `TECH-DESIGN.md` never models). This
   choice affects revocation semantics (can an admin session be force-invalidated?) and needs an explicit
   decision, possibly its own ADR.
3. **Lockout-counter storage is unmodeled.** ADR-0034 mandates three separately-anchored counters
   (dispositivo, cuenta, IP) with an escalating 60s→15min backoff, but `TECH-DESIGN.md`'s data model has
   no entity for attempt/lockout state (`Dispositivo` itself has no `bloqueado_hasta`/`intentos_fallidos`
   columns listed). In-memory storage is fragile given ADR-0037's noted cold-start/sleep behavior on
   Render (an instance restart silently resets all counters, defeating the lockout without any visible
   symptom — exactly the kind of silent failure this project's own diagnosis warns about twice). A
   persisted table is the safer default but is new schema not yet decided.
4. **Client IP determination behind Render's edge is unaddressed.** The IP-anchored counter (ADR-0034)
   needs a trustworthy client IP. `src/server/index.ts` already trusts `X-Forwarded-Proto` from the
   platform edge (`isForwardedCleartext`) but nothing yet reads `X-Forwarded-For`, and dev (loopback, no
   proxy) vs. production (behind Render's edge) will produce different remote-address shapes. Needs an
   explicit, tested trust boundary, not an assumption.
5. **The admin seed cannot be a pure `.sql` migration file**, unlike everything shipped so far.
   `scripts/migrate.ts` executes static `.sql` files verbatim and has no hook to compute an Argon2id hash
   or print a one-time plaintext password to the operator. The seed needs new TypeScript infrastructure
   (an idempotent seed script/step), and its relationship to `tests/setup/global-setup.ts` (which
   currently only calls `runMigrations()`) needs deciding: does the test suite reuse the same seed path,
   or seed its own fixture admin directly through the hashing function, bypassing the "shown once" UX for
   test purposes?
6. **`Persona` column set for this item is underspecified.** `TECH-DESIGN.md`'s `Persona` bullet lists
   `nombre, rol, pin_hash, sueldo_fijo, activo` and separately states `/admin` uses "usuario y
   contraseña" — but no literal column names for the login username or password hash are given the way
   `pin_hash` is spelled out. Following ADR-0040 (domain identifiers in Spanish, matching
   `TECH-DESIGN.md`), names like `usuario` and `contrasena_hash` are the natural fit but are not yet
   decided literally. A `debe_rotar_contrasena`-equivalent flag (or an implicit "matches seeded hash"
   check via `argon2.verify`) is also needed to enforce mandatory first-login rotation (SEC-09/ADR-0031)
   and isn't named anywhere either.
7. **Whether `Persona` is created complete or incrementally widened is undecided.** The project has an
   established precedent (`creada_por`, `vigente_desde` in #1→#2/#3) of shipping a column without its
   constraint and closing the debt in a later item. `Persona.pin_hash` (mesero-only) belongs functionally
   to #5. Should #3's migration create `Persona` with only admin-relevant columns and let #5
   `ALTER TABLE` in the PIN columns, or create the full row shape now? Either is consistent with the
   project's own pattern; propose/design should pick one explicitly.
8. **Seed values for the configuration entities are only partially derivable.** `PRD.md` fixes IGV at
   18% (`pct_igv = 1800`) and mesero commission at 5% (`pct_comision = 500`), so those two are not
   ambiguous. But `pct_merma`, `salario_cocina`, `salario_administrativo`, `costos_indirectos_mensuales`,
   and `CalendarioApertura.patron_semanal` (which days the seeded restaurant opens) have no source
   anywhere in `PRD.md`/`TECH-DESIGN.md`. `ConfiguracionOperativa.umbral_demora_min` and
   `inactividad_sesion_min` are explicitly called out in `TECH-DESIGN.md`'s own risk section as "siguen
   sin valor definido... se fijan con uso real, que este proyecto no va a tener" — meaning the backlog's
   instruction to seed these rows collides with a documented, permanent absence of a real value.
   Propose/spec needs to either pick and document explicit placeholder values (with a visible comment
   marking them as arbitrary-for-academic-purposes) or flag this as a decision that belongs in a design
   note.
9. **The "renewal on use" semantics for `Dispositivo.expira_en` may be only partially exercisable in
   this item.** ADR-0036 defines renewal as "automatic while the device is used," anchored to "every
   stream request" — but the SSE stream endpoint itself is item #4 (depends on #3), not built yet. Item
   #3 likely needs to expose a reusable verify-and-renew function/procedure that #4 later wires into the
   real stream, tested directly rather than through an end-to-end stream request. Scope boundary between
   #3 and #4 on this specific mechanic should be explicit in the proposal.
10. **This item bundles three largely independent surfaces** (admin seed+rotation+password-policy+login+
    lockout; `Dispositivo` enroll/rotate/revoke+token lifecycle; config-table seed+FK). Given the
    project's 400-changed-line PR review budget convention, `sdd-tasks` should explicitly forecast
    whether this needs chained/stacked PR slices — flagging it here so it isn't missed at tasks time.

Cross-reference checked and found not directly applicable: ADR-0017 (`Cuenta.mesero` as the sole
authorization anchor, never the table/mesa) is a pattern precedent for "authorize against the
identifying owner, never a weaker proxy" — philosophically consistent with ADR-0034's dispositivo/cuenta
split, but it's item #12's entity (`Cuenta`) and has no direct file/schema overlap with item #3.

## Ready for Proposal

Yes, with the explicit understanding that items 1-9 in Risks are open decisions for `sdd-propose`/
`sdd-spec`/`sdd-design` to make, not to inherit as already-settled. The governing ADRs
(0031/0033/0034/0036/0037/0041/0042) fully specify behavior and constraints; what's missing is
implementation mechanism (hashing library, session storage, lockout storage, IP trust boundary, exact
new columns/tables, and seed values for two config fields the project itself has flagged as permanently
undefined). None of these gaps block writing a proposal — they should be named as explicit decisions
inside it.
